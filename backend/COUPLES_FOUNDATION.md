# Couples implementation and local setup

Implementation status: 2026-10-25. This file records the working code behind the [product roadmap](../COUPLES_PRODUCT_ROADMAP.md), its verification, and the remaining release gates.

## Open the implemented app

There is one frontend app. Use `npm run dev` to develop and `npm run build` to prepare the deployed web app or Android bundle. Both use the updated account/pairing interface. There is no frontend mode flag or separate build command.

`VITE_API_URL` in the existing mobile environment configuration selects the backend. It is embedded at build time. Keep the hosted API URL when building for your phone; `localhost` on a phone points to the phone itself. The backend's `couples` Spring profile enables the updated APIs; configure this once on Render as described below.

The local backend helper below is optional development infrastructure. It does not deploy to Render.

From the repository root, in the first terminal:

```sh
./scripts/couples-dev.sh
```

In a second terminal:

```sh
cd mobile
npm ci                 # First checkout only
# For this local backend only, put VITE_API_URL=http://localhost:8082
# in mobile/.env.local (relative to the repository root).
npm run dev
```

Open **http://localhost:5173**. Create two accounts through the UI, confirm their emails in **http://localhost:8025**, then have one account create a space and share its invitation with the other. Each person explicitly confirms pairing. Separate browser profiles/private windows let you test both accounts at once. Remove the local API override before building for a phone or hosted backend.

The helper creates `.couples-dev.env` with fresh random secrets and mode `0600`; Git ignores it. It starts an isolated PostgreSQL database, Mailpit and private S3-compatible storage on loopback ports, with dedicated named volumes. It does not copy personal accounts, credentials, database records or media. Keep the generated environment file while retaining those volumes so their credentials continue to match.

If `.couples-dev.env` was generated by the earlier helper, change only `COUPLES_PUBLIC_URL` to `http://localhost:5173` and `CORS_ALLOWED_ORIGINS` to `http://localhost:5173,http://127.0.0.1:5173`. Keep its generated credentials.

| Local component | Address |
| --- | --- |
| Mobile/web app | `http://localhost:5173` |
| Couples API | `http://localhost:8082` |
| Captured verification/reset emails | `http://localhost:8025` |
| Dedicated PostgreSQL | `localhost:5544`, database `couples_local` |
| Dedicated private object storage | `http://localhost:8333` |

Docker is required. With local Java 21 and FFmpeg/`ffprobe`, the helper can run the backend through Maven. Otherwise it builds/runs the backend container, which includes FFmpeg for audio inspection. `./scripts/couples-dev.sh container` explicitly selects that container. The container uses host networking on Linux. The initial image build downloads Maven dependencies; subsequent builds reuse that layer.

The local email inbox uses [Mailpit's documented Docker image](https://mailpit.axllent.org/docs/install/docker/). Local private storage uses a pinned [SeaweedFS S3 image and its documented credentials/bucket setup](https://github.com/seaweedfs/seaweedfs). Production uses independently configured Cloudflare R2 and a transactional email provider.

```sh
./scripts/couples-dev.sh status
./scripts/couples-dev.sh stop
```

Stop retains local data volumes. For an Android update, run `npm run build` and `npx cap sync android` from `mobile`, then build/sign/install the APK using the existing Android project. A backend push does not replace the app installed on the phone.

## Normal deploy workflow and Render configuration

Make changes, run the checks below, validate the app, then push the reviewed changes. The frontend build command remains `npm run build`; its output remains `mobile/dist` (`dist` when the service root is `mobile`). Set `VITE_API_URL` to the hosted API URL in the environment that builds the frontend. There is no frontend product switch to configure.

For the backend, set `SPRING_PROFILES_ACTIVE=couples,couples-production` in the Render service environment and supply the variables in [the production environment template](.env.production.example). These settings select the updated backend through deployment configuration. Use the same hosted API URL in the Android build. Configure allowed origins for the hosted web app and Capacitor origin, plus the final App Link origin if used.

**Existing Render database:** the one-time data import is complete. Keep `COUPLES_DB_SCHEMA=couples_app` and the existing database credentials. See [DEPLOY.md](../DEPLOY.md) for normal updates.

## Working features

| Area | Implemented behavior |
| --- | --- |
| Accounts | Normalized unique email, registration gate, verification, password recovery, account name/locale/IANA timezone settings and BCrypt hashing |
| Sessions | 15-minute access JWTs tied to database sessions; 30-day refresh sessions with rotation/replay detection, logout, logout-all and password-reset revocation |
| Devices | Per-session device registration; shared-phone token reassignment, device revocation and delivery only through active sessions |
| Pairing | Verified accounts create waiting spaces; hashed single-use invitations expire after 24 hours, support an intended email, preview/confirmation, revocation and atomic capacity checks |
| Notes | Both partners compose, send or schedule. Drafts/scheduled notes are sender-only. Sent/received views show authors; sent notes are immutable; unsent notes are editable/cancellable by their sender |
| Temporary moments | Both partners create groups and publish photo/audio entries into the shared timeline. Creator-only group/entry mutations; each group contains its creator's entries and expires exactly 72 hours after creation |
| Wishes | Each person owns their list; both can browse. Only the author edits/deletes or attaches their photos. Wish photos persist independently of temporary moments |
| Watchlist | Both manage titles; each controls their own review. Scoped search, filters and pagination |
| Recipes | Both manage shared structured recipes, ordered ingredients/steps and favorites. Scoped ingredient search and pagination |
| Birthdays | Personal reminders and a personal inbox, retained after disconnect. IANA-local reminders at/after 19:00, three days and one day before the date, with idempotent durable push jobs |
| Notifications | Personal partner inbox, per-feature preferences and generic previews by default; per-device push adapter; native permission request follows an explicit user action |
| Disconnect | Recent-auth check, closed space, both memberships ended, invitations revoked, queued partner delivery cancelled, media cleanup and eventual closed-space purge |
| Privacy | Recent-auth export of the current user's own contributions; account deletion revokes access immediately and queues physical database/media removal; report-and-disconnect flow |
| Web routes | `/join`, `/verify`, `/reset`, `/delete-account` and `/privacy`; invitation tokens survive signup in session storage and URL fragments are removed from the address bar |

Access and refresh credentials stay **in memory** in the couples UI; no commercial credentials are persisted in `localStorage` or plain Preferences. Restarting/reloading the app requires login. An audited Android Keystore integration for persistent sign-in remains a release task.

The Android URL-open handler restricts accepted origins/routes. Push taps validate the expected couple, preserve pending destinations through login, and reject old relationship destinations. Actual Android App Links verification requires the final domain, application ID and signing fingerprints; those are not invented in this repository.

## Isolation, jobs and media

Every shared operation resolves current database membership, not a JWT role. Both members have equal permissions. PostgreSQL partial indexes enforce one active couple per account and slots 1/2; composite foreign keys enforce ownership for watch reviews, note participants, memory groups/assets/entries, recipe children and wish photos. All shared writes lock the couple before their resource. Invite acceptance also locks the joining account and invitation. New pairing always creates a different space.

`X-Couple-Id` binds mobile requests to the relationship where they began, including authentication-refresh replays. A stale relationship receives a conflict; membership errors refresh onboarding. A changed couple ID unmounts the Ionic route tree and its scoped caches/forms/media references. Writes are online-first; network failures require explicit retry. Notes, groups and moments use persistent creation idempotency keys.

Durable PostgreSQL jobs are created in the same transaction as business changes. Workers atomically claim bounded batches (50 per pass), use lease tokens, retry with bounded backoff, and leave exhausted jobs in `FAILED` after ten attempts. Email, push and object-storage I/O run outside business database transactions. Internal notifications are idempotent; external FCM delivery may be delayed or duplicated.

Email action tokens are reproducible HMACs of random challenge IDs under a dedicated server secret. Only hashes are stored; email jobs reference the challenge rather than storing a raw bearer token or email body. Verification expires after 24 hours and reset links after one hour. Reset, verification, invitation and refresh tokens are single-use where applicable. Login/registration/reset/invite limits persist in PostgreSQL; old counters expire after 48 hours.

Photos are decoded/re-encoded without metadata, limited to JPEG/PNG and 16 megapixels. Memory files are capped at 25 MB; wish-photo inputs at 10 MB; audio is checked for audio-only streams, decoded into normalized WAV without metadata and limited to 60 seconds of actual samples rather than trusting its duration header. The container includes `ffprobe` and `ffmpeg`. Quotas account for both wish photos and memory files (100 MiB per user and 200 MiB per couple by default), including pending deletions and the account’s files in previous closed spaces, so re-pairing cannot reset its storage quota. Upload reservations and per-member concurrent-upload checks precede storage I/O. Reservations retain exact object references after provider failure or disconnect.

Private signed reads last at most 15 minutes and never beyond a memory group's expiry. Wish photos have their independent lifecycle. Failed deletes retain references for retry; abandoned uploads are collected after 24 hours. Category expiry is never extended by uploads or edits. The legacy erasure worker cannot run in the couples profile.

## Deletion, retention and restore

Closing a couple immediately stops normal reads/writes and partner deliveries. Temporary moments are queued for cleanup at closure; other shared content is purged after the configured closed-space retention period. Local development defaults to 30 days. Production requires an explicit value (1–90 days) that must match the owner's published retention policy. This storage retention does not grant a recovery/browsing window.

Deleting an account closes its current couple, revokes its sessions/devices and queues physical erasure. Cleanup removes that account's notes (sent and received), authored shared records, own reviews, personal reminders and media; it does not erase another independent couple. Removing an authored title also removes its attached reviews. Provider failures keep the account inaccessible and the request retryable until its files are gone. Minimal request/UUID markers remain after completion; support reports are detached from the deleted identity.

**Keep the latest deletion-marker ledger independently of database backups and merge it before bringing a restored environment online.** Restored sessions and shared spaces are denied when a marker is present, even if older user/membership rows were restored. Startup reconciliation closes affected spaces, revokes access and requeues physical deletion. The automated restore-marker test covers that reconciliation. An old backup cannot contain markers for deletions that happened later: the operator must retain and reapply the newer ledger, and rehearse this alongside database/media restore.

Exports contain account settings, personal birthday reminders, the user's own sent/private notes, authored moments/wishes/recipes/watch titles and their reviews in the current accessible couple. Recipes include their ingredients/steps; photo/audio references are temporary signed links. Old closed spaces are not exported through normal APIs. No data is automatically transferred into a new relationship.

`/privacy` reports the running system's actual rules and `/delete-account` provides browser login and deletion without the installed app. These technical disclosures do not replace launch-country legal review, the final published privacy policy, backup-retention disclosures or Google Play Data safety declarations.

## Migrations and deployment

The `couples` profile uses separate `COUPLES_*` database/JWT/R2/Firebase configuration, Flyway and `ddl-auto: validate`. Automatic baseline and Flyway clean are disabled. Migrations currently cover fresh monolith schema, couple constraints, identity/pairing/jobs, bidirectional features, privacy records, recipe/wish isolation and rate-limit retention. Dormant legacy-module tables remain because Hibernate validates the modular monolith's entities; their legacy endpoints/workers are disabled.

The one-time importer and cutover scripts have been removed. Keep all versioned Flyway migrations unchanged, including V8: its imported-media records still authorize cleanup of existing files. Startup applies future migrations and grants the runtime role access to the app tables. The old `public` schema remains an independent frozen snapshot; normal updates do not copy from it.

For the hosted app, activate **both** `couples,couples-production`. The additional profile/guard requires distinct migration/runtime database roles, a public HTTPS origin, distinct signing secrets, private HTTPS media configuration, a support address, Firebase credentials, explicit retention and schema validation. The private phase uses `COUPLES_EMAIL_ENABLED=false`, disabled public registration and an explicit `COUPLES_PRIVATE_ACCOUNT_EMAILS` list. Those approved existing accounts need no verification email; other accounts cannot sign in or reuse sessions. No SMTP provider is required. Addresses remain unverified in the database.

Required configuration follows `application-couples.yml` and `application-couples-production.yml`; the private `.render.env` contains the ongoing Render settings and reuses the existing database/JWT/R2/Firebase configuration. See [DEPLOY.md](../DEPLOY.md) for the current exact steps. At official launch, configure your chosen secure SMTP provider and sender, set `COUPLES_EMAIL_ENABLED=true`, validate verification/recovery, then enable public registration when ready. Email verification applies to existing accounts too once enabled. Configure CORS/native App Link origins deliberately. The root Docker image serves the SPA entry point for public routes.

CI runs backend tests with real PostgreSQL/Testcontainers, migration validation, the normal mobile build, lint and the runtime npm vulnerability audit. Release the same reviewed image through environments. Configure operational alerts for `outbox_jobs.state='FAILED'`, oldest ready job, deletion age, stored-byte totals, database capacity and provider spending; database rows alone are not a deployed monitoring/alerting service.

## Verification

Initial local verification (2026-10-25): **99 backend tests passed**, including 36 real-PostgreSQL integration tests; both then-existing mobile builds, lint, the runtime vulnerability audit and the live API/SMTP/private-storage smoke test passed. After consolidating the frontend, the normal `npm run build` and lint passed again. Lint retains three existing warnings.

```sh
cd backend
./mvnw test
cd ../mobile
npm run build
npm run lint
cd ..
python3 backend/scripts/couples-smoke.py
```

The smoke test is loopback-only and creates four synthetic accounts through registration, verifies them through captured SMTP email, pairs two independent couples, and exercises the real API/worker/S3 stack. It checks note privacy and both directions, due-note delivery, real photo/audio upload and private signed reads, cross-couple isolation, wishlist authorship, recipes, personal birthdays, disconnect and actual object removal after account deletion. Its default cleanup removes only its synthetic accounts/files.

Browser checks use two isolated synthetic accounts and a 390×844 mobile viewport. See [validation artifacts](../design-validation/couples-beta/README.md). No intimate production fixtures are used.

## Dependency checks

Capacitor Android/core/CLI are updated to 8.5.3; the native patch covers the [reported internal-proxy navigation vulnerability](https://github.com/advisories/GHSA-rvm3-566m-v7fv). CLI tooling is a development dependency. The unused `@capacitor/assets` generator was removed: the existing brand-sync script copies the supplied assets directly and explicitly avoids regenerating them. A compatible Babel runtime override fixes the old recorder dependency without downgrading the recorder API.

At initial verification, `npm run audit:runtime` reported zero runtime vulnerabilities. Full npm audit still reported three moderate development-tooling entries in the CLI/xcode/uuid chain; review those before release. Runtime dependency checks and the app build are separate checks. No native APK was installed or distributed as part of this work.
